## 坑 #1 · .venv 不能跨目录复制

**什么情况下会踩**：从其他项目复制 `.venv` 过来，或者改了项目目录名/路径之后直接用。

**根因**：`.venv/bin/` 下的脚本 shebang 行包含创建时的**绝对路径**，换了路径就找不到 Python 解释器。

**解法**：
```bash
rm -rf .venv
uv sync
```

## 坑 #2 · YAML 配置新增字段后忘了改 dataclass

**什么情况下会踩**：在配置文件或 `.env` 里加了新变量，但对应的 Python dataclass（如 `MilvusConfig`）没有同步添加字段。

**根因**：`OmegaConf` 在合并配置时会校验 dataclass 结构，多出来的字段会报合并错误（如果用 OmegaConf），或者直接被忽略导致静默错误（如果用 `.env` + dataclass）。

**解法**：修改配置类时，同步检查对应的 `app/conf/*.py` 里的 dataclass，加上新字段（含类型注解）。

## 坑 #3 · VPN 的 Fake IP 模式会拦截 Milvus / MinIO 请求

**什么情况下会踩**：开着 VPN（尤其是 TUN/Fake IP 模式），访问 `localhost:19530` 或 `localhost:9000` 报连接错误，但 `docker ps` 显示容器正常运行。

**根因**：TUN 模式会接管系统的所有网络请求，Fake IP 可能将某些 localhost 请求路由到 VPN 隧道，导致请求根本没到 Docker 容器。

**解法**：
1. 在 VPN 规则里把 `127.0.0.1` 和 `localhost` 加入直连列表
2. 或者关掉 VPN 测试
3. 代码层面：在 httpx 或 requests 里设置 `proxies={}` 绕过系统代理

## 坑 #4 · Milvus 容器启动时间比 server 启动时间长

**什么情况下会踩**：`docker-compose up -d` 之后立刻启动 import_server 或 query_server，报 Milvus 连接错误。

**根因**：`docker-compose up -d` 只等容器进程启动，不等服务完全 ready。Milvus 需要 etcd 和 minio 都就绪后才能接受连接，完整启动需要 20-30 秒。

**解法**：`docker-compose up -d` 后等 30 秒，再用 `curl http://localhost:9091/healthz` 确认 ready，然后再启动 server。
```bash
docker-compose up -d
sleep 30
curl http://localhost:9091/healthz
# 看到 {"status":"ok"} 再启动 server
```

## 坑 #5 · BGE-M3 首次加载时间很长，容易误判为卡死

**什么情况下会踩**：启动 import_server 后终端长时间没有输出，以为进程卡死。

**根因**：BGE-M3 是大型多语言 embedding 模型，首次加载（从磁盘读模型权重、初始化 tokenizer）需要 1-3 分钟，期间没有任何进度输出。

**解法**：等待，不是报错。用 `top` 或 Activity Monitor 观察 Python 进程的 CPU 使用率，有 CPU 活动说明在正常加载。

## 坑 #6 · yyyyMMdd 整数日期格式让 LLM 生成错误 SQL（如果后续扩展 NL2SQL）

**什么情况下会踩**：存储层如果有日期字段用整数格式（如 `20240101`），LLM 生成查询条件时会直接用字符串 `"2024-01-01"` 去比较，类型不匹配导致结果错误。

**根因**：LLM 不了解底层存储格式，会按自然语言习惯生成日期条件。用 prompt 打补丁不可靠（每次生成都有随机性），根本解决方案是改数据模型。

**解法**：在数据入库时把日期统一存为 `datetime` 或 ISO 格式字符串，不用整数。这是数据模型层面的问题，prompt 补丁不能根治。

## 坑 #7 · 向量维度不匹配导致 Milvus 写入失败

**什么情况下会踩**：修改了 embedding 模型（比如从 BGE-M3 换成其他模型），但 Milvus 里已有 Collection 是按原模型的维度建的。

**根因**：Milvus Collection 建立时就固定了向量维度（BGE-M3 dense 是 1024 维），新模型输出维度不同时写入会报维度不匹配错误。

**解法**：换模型时必须重建 Collection。先删除原有 Collection，然后重新导入数据。
```bash
# 在 Python 里
from pymilvus import Collection
Collection("rag_chunks").drop()
# 然后重新运行导入流程
```

## 坑 #8 · HyDE 搜索的 LLM 调用失败不影响最终结果（静默降级）

**什么情况下会踩**：DashScope API Key 额度用完或暂时不可用，HyDE 搜索的 LLM 调用失败，但查询还是返回了结果。

**根因**：`main_graph.py` 里三路搜索是并行的，RRF 融合会处理空结果。HyDE 节点失败时如果没有显式错误处理，它的结果就是空列表，对最终结果没有影响——但这也意味着你不知道 HyDE 在工作。

**解法**：在 `node_search_embedding_hyde.py` 里加日志，明确记录 HyDE 是否成功生成假设文档。评估时对比有 HyDE 和没有 HyDE 的准确率，确认它在起作用。
