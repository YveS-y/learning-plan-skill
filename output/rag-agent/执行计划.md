## 📍 现状诊断

### 已完成
- **导入流程节点**（`app/import_process/agent/nodes/`）：7个节点全部实现——`node_entry`（路由）、`node_pdf_to_md`（MineRU 转换）、`node_md_img`（图片处理）、`node_document_split`（分块）、`node_item_name_recognition`（实体识别）、`node_bge_embedding`（向量化）、`node_import_milvus`（写库）
- **导入流程图**（`app/import_process/agent/main_graph.py`）：完整的 LangGraph StateGraph，含 PDF/MD 路由分支
- **导入 API**（`app/import_process/api/import_server.py`）：3个接口已实现——`GET /import`（页面）、`POST /upload`（上传+触发图）、`GET /status/{task_id}`（进度查询）
- **查询流程节点**（`app/query_process/agent/nodes/`）：7个节点全部实现——`node_item_name_confirm`（实体确认）、并行三路搜索（embedding + HyDE + web_search_mcp）、`node_rrf`（RRF融合）、`node_rerank`（重排序）、`node_answer_output`（LLM生成+历史写入）
- **查询流程图**（`app/query_process/agent/main_graph.py`）：完整图，含并行搜索 + 条件路由
- **查询 API**（`app/query_process/api/query_server.py`）：6个接口全部实现——健康检查、页面、发起提问、SSE 流式输出、历史查询、历史删除
- **前端**：`chat.html` + `import.html` 均已存在
- **配置层**（`app/conf/`）：8个配置类全齐（embedding、lm、milvus、mineru、minio、reranker、bailian_mcp + mongodb 在代码中直接用）

### 有缺口
- **导入进度追踪**（`app/import_process/api/import_server.py`）：`run_import_graph()` 函数里的 `add_running_task` / `add_done_task` 调用被注释掉，导致 `GET /status/{task_id}` 永远返回 pending，前端进度条不更新
- **基础设施启动脚本**：没有 `docker-compose.yml`，Milvus / MongoDB / MinIO 要手动启动，环境搭建全靠记忆或文档

### 未开始
- 评估数据集（测试问题 + 标准答案）
- 准确率/召回率量化测试
- 作品集文档（项目总结、踩坑记录、项目闪卡）

### 当前能走通的路径
代码上，导入和查询的完整链路都已实现。**但因为缺 docker-compose.yml，没有一键启动基础设施的方式**，每次需要手动启动 Milvus / MongoDB / MinIO，然后分别启动 import_server 和 query_server。
从技术上讲，走通是可能的，但操作繁琐且没有验证记录。

### 距离"完成"还差什么
1. **docker-compose.yml**：没有就每次启动都是负担，是后续所有工作的前置
2. **导入进度追踪修复**：影响用户体验，是功能完整性的问题
3. **端到端验证**：导入一个文件、查到内容，这个闭环目前没有被验证过
4. **评估体系**：无法量化说出系统准确率，作品集说服力差
5. **文档**：没有文档就无法展示给别人

### T1.1 · 创建 docker-compose.yml

**现在的情况**：没有 docker-compose.yml，Milvus / MongoDB / MinIO 必须手动一条条命令启动，且没有版本和端口的统一记录。

**做完之后**：一条命令 `docker-compose up -d` 启动所有基础设施，重启环境不再痛苦。

**为什么先做这个**：启动流程繁琐会让后续每次调试都多一层摩擦，而且这是 import_server 和 query_server 启动的前置。

**步骤**：

1. 在项目根目录新建 `docker-compose.yml`，内容如下：

   ```yaml
   version: "3.8"
   services:
     milvus-etcd:
       image: quay.io/coreos/etcd:v3.5.5
       environment:
         - ETCD_AUTO_COMPACTION_MODE=revision
         - ETCD_AUTO_COMPACTION_RETENTION=1000
         - ETCD_QUOTA_BACKEND_BYTES=4294967296
         - ETCD_SNAPSHOT_COUNT=50000
       volumes:
         - milvus_etcd:/etcd
       command: etcd -advertise-client-urls=http://127.0.0.1:2379 -listen-client-urls http://0.0.0.0:2379 --data-dir /etcd

     milvus-minio:
       image: minio/minio:RELEASE.2023-03-13T19-46-17Z
       environment:
         MINIO_ACCESS_KEY: minioadmin
         MINIO_SECRET_KEY: minioadmin
       volumes:
         - milvus_minio:/minio_data
       command: minio server /minio_data
       healthcheck:
         test: ["CMD", "curl", "-f", "http://localhost:9000/minio/health/live"]
         interval: 30s
         timeout: 20s
         retries: 3

     milvus:
       image: milvusdb/milvus:v2.4.0
       command: ["milvus", "run", "standalone"]
       environment:
         ETCD_ENDPOINTS: milvus-etcd:2379
         MINIO_ADDRESS: milvus-minio:9000
       volumes:
         - milvus_data:/var/lib/milvus
       ports:
         - "19530:19530"
         - "9091:9091"
       depends_on:
         - milvus-etcd
         - milvus-minio

     mongodb:
       image: mongo:7.0
       ports:
         - "27017:27017"
       volumes:
         - mongo_data:/data/db

     minio:
       image: minio/minio:latest
       ports:
         - "9000:9000"
         - "9001:9001"
       environment:
         MINIO_ROOT_USER: minioadmin
         MINIO_ROOT_PASSWORD: minioadmin
       volumes:
         - app_minio_data:/data
       command: server /data --console-address ":9001"

   volumes:
     milvus_etcd:
     milvus_minio:
     milvus_data:
     mongo_data:
     app_minio_data:
   ```

   > 注意：Milvus standalone 自带一个内部 minio，和应用层用的 minio 是两个不同容器，端口不冲突。

2. 启动：
   ```bash
   docker-compose up -d
   ```
   预期看到：所有容器 `Started` 或 `Healthy`，无 `Exit` 状态

3. 验证 Milvus 连通：
   ```bash
   curl http://localhost:9091/healthz
   ```
   预期看到：`{"status":"ok"}`

**验收标准**：`docker-compose ps` 显示所有容器状态为 `Up`，Milvus healthz 返回 ok。

**出问题先查**：
- `port is already allocated` → 本机有端口冲突 → 修改 docker-compose.yml 里的宿主机端口（左边的数字）
- Milvus 容器反复重启 → etcd 或 minio 还没 ready → `docker-compose logs milvus-etcd` 看具体原因
- `Cannot connect to the Docker daemon` → Docker 没启动 → 打开 Docker Desktop

**状态**：⏳ 待执行

### T2.1 · 修复导入进度追踪

**现在的情况**：`import_server.py` 里 `run_import_graph()` 函数的 `add_running_task` / `add_done_task` 调用被注释掉，`GET /status/{task_id}` 永远返回 `pending` 状态。

**做完之后**：每个节点执行时更新状态，前端轮询 `/status` 能看到实时进度。

**为什么先做这个**：这是已经写了一半的功能，注释掉的代码说明作者有设计但没完成。现在跑通后可以直接补完。

**步骤**：

1. 打开 `app/import_process/api/import_server.py`，找到 `run_import_graph()` 函数

2. 找到被注释掉的 `add_running_task` / `add_done_task` 部分，理解数据结构（`running_tasks` / `done_tasks` 字典的键值格式）

3. 在 LangGraph 流式事件回调里，每次节点开始时调用 `add_running_task(task_id, node_name)`，节点完成时调用 `add_done_task(task_id, node_name)`：

   ```python
   async for event in graph.astream_events(state, version="v2"):
       if event["event"] == "on_chain_start":
           node_name = event.get("name", "")
           if node_name.startswith("node_"):
               add_running_task(task_id, node_name)
       elif event["event"] == "on_chain_end":
           node_name = event.get("name", "")
           if node_name.startswith("node_"):
               add_done_task(task_id, node_name)
   ```

   > 具体 event 类型和 node_name 格式以实际 `astream_events` 输出为准，先加日志打印看看。

4. 用 Postman 或 curl 上传文件，同时轮询 `/status/{task_id}`：
   ```bash
   curl http://localhost:8001/status/{task_id}
   ```
   预期看到：`running_nodes` 随进度变化，`done_nodes` 逐渐增加

**验收标准**：上传一个文件，多次请求 `/status/{task_id}` 能看到节点状态变化，最终 `status` 变为 `completed`。

**出问题先查**：
- 所有节点都出现在 `running_nodes` 但没移到 `done_nodes` → `add_done_task` 的触发条件不对 → 打印 `event["event"]` 的值，确认 end 事件名
- `task_id not found` → 上传接口生成的 task_id 和状态存储的 key 不一致 → 检查 `running_tasks` 字典的 key 格式

**状态**：⏳ 待执行

### T3.2 · 编写评估脚本

**现在的情况**：没有自动化评估脚本。

**做完之后**：一条命令跑完所有测试用例，输出准确率报告。

**步骤**：

1. 新建 `test/eval.py`：

   ```python
   import json
   import httpx
   import asyncio

   async def run_eval():
       with open("test/eval_cases.json") as f:
           cases = json.load(f)

       results = []
       async with httpx.AsyncClient() as client:
           for case in cases:
               resp = await client.post(
                   "http://localhost:8000/query",
                   json={"question": case["question"], "stream": False}
               )
               # 读取 SSE 或同步结果，检查 expected_keywords 是否出现在回答里
               answer = ...  # 解析 resp
               hit = all(kw in answer for kw in case["expected_keywords"])
               results.append({"id": case["id"], "hit": hit, "answer": answer})

       passed = sum(1 for r in results if r["hit"])
       print(f"通过：{passed}/{len(results)}（{passed/len(results)*100:.1f}%）")
       # 打印失败的用例
       for r in results:
           if not r["hit"]:
               print(f"  ❌ {r['id']}: {r['answer'][:100]}")

   asyncio.run(run_eval())
   ```

2. 跑评估，记录 baseline：
   ```bash
   uv run python test/eval.py
   ```
   预期看到：通过率报告 + 失败用例清单

**验收标准**：脚本能跑完，输出通过率数字（不要求通过率高，先有基线）。

**状态**：⏳ 待执行

### T3.3 · 基于评估结果迭代

**现在的情况**：有了 baseline 数字，能看到哪些问题答错了。

**做完之后**：通过率 ≥ 85%（参考 nl2sql 的 96.7%，RAG 难度更高，85% 是合理目标）。

**迭代方向**（按最常见的失败原因排序）：

| 失败模式 | 可能原因 | 调整方向 |
|---------|---------|---------|
| 回答说"没有找到相关信息" | 召回率低，块没检索到 | 调整 chunk_size / 检查 embedding 质量 |
| 回答模糊不精确 | rerank 没把最相关块排第一 | 检查 reranker 权重 / 增加 top_k |
| 答非所问 | item_name_confirm 节点路由错误 | 检查实体识别节点的输出 |

调整后重跑 `eval.py`，记录新的通过率，写入踩坑记录。

**验收标准**：通过率 ≥ 85%，失败用例有分析说明。

**状态**：⏳ 待执行
