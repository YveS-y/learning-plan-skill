## 一、RAG 体系

### R1 · Embedding（向量化）✅
> 把文本映射成高维空间中的一个数字向量，语义相近的文本在空间中距离也近。

**为什么重要**：向量是 RAG 检索的基础，没有 Embedding 就没有语义搜索。

**直觉检验题**：两段话「逾期 30 天」和「M1 客户」，用关键词搜索找不到联系，向量搜索能不能？为什么？

**框架层节点**：RAG 体系 > 检索策略

---

### R2 · 稠密向量 vs 稀疏向量 ✅
> 稠密向量：每个维度都有值（BGE-M3 输出 1024 维，全部非零），捕捉语义相似度。
> 稀疏向量：绝大多数维度为 0，只有关键词出现的维度有权重值（类 BM25），捕捉关键词匹配。

**为什么重要**：单用稠密会漏精确关键词匹配，单用稀疏会漏语义相近但措辞不同的内容；混合才能兼顾。

**直觉检验题**：用户问「催收管理办法第 3 条」，稠密和稀疏哪路更可能召回到正确内容？

**框架层节点**：RAG 体系 > 检索策略

---

### R3 · ANN（近似最近邻搜索）✅
> 在百万向量中找最相似的 top-k，暴力精确搜索太慢（O(n)），ANN 允许少量误差换取速度。

**为什么重要**：RAG 生产环境向量库动辄百万条，ANN 是让向量搜索可用的前提。

**直觉检验题**：ANN「近似」会不会影响召回质量？什么场景下这个误差可以接受，什么场景下不行？

**框架层节点**：RAG 体系 > 检索策略

---

### R4 · HNSW（图索引）✅
> 层级可导航小世界图。把向量建成多层图，上层稀疏快速定位大方向，下层密集精细找邻居，查询时从上往下缩小范围。适合稠密向量的 ANN 搜索。

**为什么重要**：Milvus 里稠密向量用 HNSW，是 ANN 的主流工程实现。

**直觉检验题**：为什么 HNSW 不适合稀疏向量？稀疏向量的「邻居关系」为什么失效？

**框架层节点**：RAG 体系 > 检索策略

---

### R5 · 倒排索引（稀疏向量用）✅
> 只记录哪些文档在哪些维度上有非零值，查询时跳过所有零维，只对非零维做计算。稀疏向量大量为零，倒排索引天然契合。

**为什么重要**：Milvus 里稀疏向量用 SPARSE_INVERTED_INDEX，比 HNSW 更高效处理高维稀疏数据。

**直觉检验题**：如果硬给稀疏向量用 HNSW，会出什么问题？

**框架层节点**：RAG 体系 > 检索策略

---

### R6 · 2 段切片策略 ✅
> 先按语义边界切（Markdown 标题），保证语义完整；再按尺寸精修（chunk 超 2000 字符拆分，不足 500 合并），控制 token 成本。

**为什么重要**：切片质量直接决定 RAG 召回质量，一刀切固定字数会割裂语义。

**直觉检验题**：政策条文「第 3.2 条：逾期 30 天以上客户须……（共 300 字）」，不做语义切、直接固定 200 字切，会出什么问题？

**框架层节点**：RAG 体系 > 分块策略

---

### R7 · HyDE（假设文档嵌入）⚠️
> 用户的问句（"X 是什么？"）和知识库里的答句（"X 是……"）在向量空间中可能距离很远。HyDE：先让 LLM 生成一段「假设答案」，再用假设答案的向量去检索，拉近问句和文档的距离。

**为什么重要**：提升概念解释类问题的召回率，是 knowledge_base 查询图的三路召回之一。

**直觉检验题**：「催收员第一句话该说什么」这种问题，HyDE 和直接向量检索哪个效果更好？「M1 逾期金额是多少」这种问题呢？为什么不同？

**框架层节点**：RAG 体系 > 检索策略 > HyDE

---

### R8 · RRF（倒数排名融合）❌
> 多路召回的结果分数量纲不同，无法直接加权。RRF 按排名而非分数合并：score = Σ(1/(60+rank))，排名越靠前贡献越大，常数 60 防止 rank=1 时分数过大。

**直觉检验题**：同一个 chunk 同时出现在 3 路召回里，它的 RRF 得分怎么算？比只出现在 1 路的高多少？

**框架层节点**：RAG 体系 > 多路召回与融合

---

### R9 · Cross-Encoder Reranker（精排）❌
> 召回阶段用 Bi-Encoder（向量距离，快），精排阶段用 Cross-Encoder（问题+文档拼接一起送模型，慢但准）。Reranker 只能对小候选集（20-50 条）精排，不能做召回。

**直觉检验题**：为什么 Reranker 不能替代召回阶段？如果直接用 Reranker 对全量文档打分会怎样？

**框架层节点**：RAG 体系 > 重排序

---

### R10 · 幻觉治理（信贷场景）❌
> LLM 在知识库为空时会「编造」答案。工程层面：检测 retrieved_docs 为空时直接返回「知识库中无相关内容」，不进入 LLM 生成。

**直觉检验题**：信贷合规场景的幻觉风险比通用场景大在哪里？工程层面还有哪些手段可以减少幻觉？

**框架层节点**：RAG 体系 > 生产级坑点

---

## 二、Agent 编排体系

### A1 · LangGraph 节点/边/状态 ✅
> 节点（Node）：一个 Python 函数，读取 State、处理、写回 State。边（Edge）：节点间的连接，可以是固定的也可以是条件的。State：图里所有节点共享的数据字典，贯穿整个执行流程。

**为什么重要**：LangGraph 是本项目群的编排基础，所有 Agent 图都基于这三个概念。

**直觉检验题**：两个节点需要共享一个变量（如 item_name），用全局变量 vs State，各有什么问题？

**框架层节点**：Agent 体系 > 单 Agent 架构

---

### A2 · 条件路由 ✅
> `add_conditional_edges`：节点执行后，根据返回值动态决定走哪条边。本质是图里的 if-else，让 Agent 能根据状态分叉处理。

**为什么重要**：导入图的文件类型判断（PDF / MD / 其他）就是条件路由，是 Agent 应对复杂场景的基础能力。

**直觉检验题**：条件路由函数里抛出异常，图会怎么处理？和路由到 END 有什么区别？

**框架层节点**：Agent 体系 > 单 Agent 架构 > 节点/边/状态

---

### A3 · 并行节点（fan-out）⚠️
> LangGraph 支持一个节点 fan-out 到多个下游节点并行执行，再 fan-in 汇聚结果。knowledge_base 查询图的 3 路并行召回就用了这个模式。

**为什么重要**：并行执行可以大幅降低多路 I/O 的总延迟（3 路串行 vs 并行的差距）。

**直觉检验题**：3 路并行召回，其中 1 路（联网搜索）超时了，整个图会怎么处理？如何设计才能让超时不阻塞其他两路？

**框架层节点**：Agent 体系 > 单 Agent 架构

---

### A4 · Multi-Agent 编排 ❌
> 多个 Agent 协作：主 Agent 负责路由和编排，子 Agent 各自负责一类任务（RAG 问答 / SQL 查询 / 联网搜索）。deep_search_pro 的三子 Agent 模式。

**直觉检验题**：单 Agent + 多工具 vs Multi-Agent，什么时候该拆分成多 Agent？拆分的代价是什么？

**框架层节点**：Agent 体系 > Multi-Agent 协作

---

### A5 · 客户端单例模式 ✅
> 模块级变量 + 懒加载：首次访问时初始化客户端（Milvus/MongoDB），后续复用同一个连接，避免每次请求都建立新连接的开销。

**为什么重要**：数据库连接是重资源，单例是 Agent 服务的标准工程实践。

**直觉检验题**：多线程环境下，单例的懒加载初始化会有什么竞态问题？怎么防？

**框架层节点**：Agent 体系 > 工程基础

---

### A6 · ContextVar 会话隔离 ❌
> Python 的 `contextvars.ContextVar`：同一进程内不同协程/请求之间的变量互不干扰。deep_search_pro 用它隔离多用户并发会话的状态。

**直觉检验题**：不用 ContextVar、直接用模块级全局变量存会话状态，两个用户并发请求会出什么问题？

**框架层节点**：Agent 体系 > 状态管理

---

### A7 · SSE vs WebSocket ❌
> SSE（Server-Sent Events）：HTTP 单向推送，服务端 → 客户端，实现简单，适合流式问答输出。WebSocket：全双工，适合需要双向实时通信的场景（如 deep_search_pro 的任务监控）。

**直觉检验题**：RAG 问答用 SSE、任务监控用 WebSocket，这个选择的依据是什么？如果反过来用会怎样？

**框架层节点**：Agent 体系 > 工程基础

## 三、Text-to-SQL 体系

### S1 · 元知识检索 ✅
> 把数据库的表结构、字段含义、业务指标定义（元数据）向量化存入向量库，用户问题先检索相关元数据，再拼进 Prompt 生成 SQL，避免把所有表结构塞进 Prompt。

**为什么重要**：数据库表多时 Prompt 会超长，元知识检索是 Text-to-SQL 的工程关键。

**直觉检验题**：元知识检索召回了错误的表（语义相近但不是正确答案），SQL 会出什么问题？怎么降低这个风险？

**框架层节点**：Text-to-SQL 体系 > Schema 理解

---

### S2 · SQL 生成 Prompt 设计 ✅
> 系统 Prompt 里注入：业务上下文 + 召回的表结构 + 字段含义 + 历史 Q&A 示例（few-shot）。减少 LLM 自由发挥，提高 SQL 准确率。

**直觉检验题**：few-shot 示例应该放什么样的 Q&A？随机放好还是针对用户当前问题召回相似示例好？

**框架层节点**：Text-to-SQL 体系 > SQL 生成与校验

---

### S3 · SQL 自愈机制 ✅
> SQL 执行失败时，把错误信息反馈给 LLM，让它修正 SQL 再试，最多重试 N 次。LangGraph 里用条件路由实现「执行失败 → 修正 → 重试」的循环。

**直觉检验题**：SQL 自愈的终止条件是什么？如果 LLM 每次修正后还是报相同的错，怎么跳出死循环？

**框架层节点**：Text-to-SQL 体系 > 错误修正循环

---

### S4 · 多路异构召回 ❌
> data-agent 同时从向量库（语义）+ ElasticSearch（关键词）+ 结构化元数据（精确匹配）三路召回相关表和字段，融合后喂给 LLM。

**直觉检验题**：只用向量语义召回，「放款金额」和「贷款本金」会不会被认为是同一个字段？多路召回怎么解决这个问题？

**框架层节点**：Text-to-SQL 体系 > Schema 理解

---

## 四、大模型底层

### L1 · Token 与 Context Window ❌
> Token 是 LLM 处理文本的基本单位（约 1 个汉字 = 1.5 token）。Context Window 是模型一次能处理的最大 token 数，超出则截断。

**直觉检验题**：一份 50 页合规文档约 10 万字，直接喂给 context window 128k 的模型行不行？为什么 RAG 还是必要的？

**框架层节点**：大模型底层 > 推理

---

### L2 · Temperature（温度）❌
> 控制 LLM 输出的随机性。temperature=0：确定性最高，每次输出相同；temperature=1：创意最强，每次输出不同。

**直觉检验题**：SQL 生成应该用高 temperature 还是低 temperature？RAG 的答案生成呢？信贷合规场景呢？

**框架层节点**：大模型底层 > 推理

---

### L3 · Prompt Engineering 基础 ❌
> 系统提示（角色定义 + 约束） + 用户提示（任务 + 上下文） + few-shot 示例。结构化的 Prompt 比自然语言描述准确率更高。

**直觉检验题**：让 LLM 从文档里提取 item_name，Prompt 里加 few-shot 示例比只写「请提取文章标题」好在哪里？什么时候 few-shot 反而会帮倒忙？

**框架层节点**：大模型底层 > 推理

---

### L4 · Streaming 流式输出 ❌
> LLM 生成是逐 token 输出的，流式返回（yield token）比等待完整响应后一次性返回用户体验更好，响应感知延迟从「等整篇文章」降为「看到第一个字」。

**直觉检验题**：流式输出时，前端如何知道 LLM 已经输出完毕了？SSE 里怎么发送「结束信号」？

**框架层节点**：大模型底层 > 推理

---

### L5 · SFT / LoRA / RLHF ❌
> SFT（监督微调）：用标注数据调整模型权重，让模型学会特定任务。LoRA：低秩矩阵微调，只训练少量参数，成本远低于全量微调。RLHF：基于人类反馈的强化学习，ChatGPT 用来对齐人类偏好。

**直觉检验题**：信贷合规 Agent 要提升对「逾期分层催收话术」的理解，应该用 RAG 还是 SFT？各自适合什么情况？

**框架层节点**：大模型底层 > 训练

---

### L6 · 量化与本地部署 ❌
> 量化：把模型权重从 float32 压缩为 int8/int4，降低显存占用和推理时间，轻微损失精度。knowledge_base 里 BGE-M3 本地推理就是量化后的模型。

**直觉检验题**：BGE-M3 为什么选择本地部署而不是调 API？本地部署的成本和好处分别是什么？

**框架层节点**：大模型底层 > 推理优化

---

## 五、工程判断力

### E1 · 幂等设计 ✅
> 同一操作执行多次和执行一次的结果相同。`has_collection` 检查 → 不存在才建表；写入前检查 chunk_id 是否已存在。防止重复执行导致数据重复。

**直觉检验题**：导入图重跑（比如节点失败后重试），如果 Milvus 建表没有幂等保护，会出什么问题？

**框架层节点**：工程判断力 > 生产级取舍

---

### E2 · 失败兜底策略 ⚠️
> 全回滚（原子性，代价高）vs 跳过失败条目+日志（部分成功，可补录）vs 整批重试（网络抖动有效，永久失败死循环）。没有最优解，取决于业务对一致性 vs 可用性的要求。

**直觉检验题**：信贷合规文档导入失败了 5 个 chunk，选择「跳过+日志」，后续查询时这 5 个 chunk 的内容永远查不到，可以接受吗？什么场景下必须全回滚？

**框架层节点**：工程判断力 > 生产级取舍

---

### E3 · 批处理与显存/吞吐权衡 ✅
> batch_size 不是越大越好：太大 → GPU OOM；太小 → 吞吐低、失败重试代价小但总时间长。BGE-M3 用 batch_size=5，是显存 / 吞吐 / 失败重试成本三者的帕累托点。

**直觉检验题**：如果机器显存升级了，batch_size 就应该调大吗？还有什么因素要考虑？

**框架层节点**：工程判断力 > 参数直觉

---

### E4 · LangGraph State 持久化 ❌
> LangGraph 默认 State 在内存中，进程重启后丢失。生产环境需要持久化 State（如写入 Redis/DB），才能支持断点续跑和多实例部署。

**直觉检验题**：knowledge_base 导入图跑到一半进程崩了，重启后要从哪个节点重跑？如果 State 持久化了呢？

**框架层节点**：工程判断力 > 生产级取舍

---

### E5 · MCP（模型上下文协议）❌
> Anthropic 提出的标准化工具调用协议，让 LLM 能以统一方式调用外部工具（搜索、数据库、API）。knowledge_base 的联网搜索节点用了 MCP 工具。

**直觉检验题**：MCP 和直接写 Python 工具函数相比，多了什么？标准化协议对多 Agent 协作的好处是什么？

**框架层节点**：Agent 体系 > 工具调用与 MCP

## 六、客服 Agent 体系（llm_customer_service）

> 学习角度：不精读源码，从 LLM + Agent 设计视角理解，用于 vibe coding 重构参考

### C1 · 对话状态管理（DST）❌
> 多轮对话中跟踪用户意图、槽位（slot）填充状态、历史对话上下文。决定下一步该问什么、该执行什么动作。

**直觉检验题**：用户说「我要催收 M2 的客户」，下一句说「等等，先查一下他的还款记录」，对话状态管理需要记录什么才不会丢失上下文？

**框架层节点**：Agent 体系 > 状态管理

---

### C2 · Flow 引擎 vs LangGraph ❌
> llm_customer_service 用自定义 Flow 引擎（规则驱动的对话流程）；LangGraph 用图结构（节点+边+状态）。Flow 更可控但灵活性低；LangGraph 更灵活但调试复杂。

**直觉检验题**：客服催收场景（固定话术流程）用 Flow 引擎还是 LangGraph？开放式问答场景呢？

**框架层节点**：Agent 体系 > 单 Agent 架构

---

### C3 · NLG（自然语言生成）❌
> 根据对话状态和动作，生成自然语言回复。可以是模板填充（可控）、LLM 直接生成（灵活）或两者结合（模板框架 + LLM 填充细节）。

**直觉检验题**：催收开场白用模板 vs 用 LLM 自由生成，合规风险有什么不同？

**框架层节点**：Agent 体系 > 状态管理

---

### C4 · 多通道适配 ❌
> 同一个对话逻辑要适配不同输入渠道（REST API / WebSocket / 控制台）。通道层负责消息格式转换，核心逻辑与通道解耦。

**直觉检验题**：信贷催收场景需要同时支持「电话 AI 助手」和「App 内聊天」两个通道，共用同一套对话逻辑，架构上怎么隔离通道差异？

**框架层节点**：Agent 体系 > 工程基础
